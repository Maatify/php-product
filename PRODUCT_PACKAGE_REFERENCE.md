# Product Package Reference

**Package:** `maatify/php-product`
**Status:** Every approved contract is implemented; nothing is released. This file is the canonical root Package Reference path required by the Package Building Standard (`/{PACKAGE_NAME}_PACKAGE_REFERENCE.md`), and the public runtime inventory is under [Implemented Public API](#implemented-public-api).
**Architecture contract:** [`docs/architecture/PRODUCT_V1_ARCHITECTURE_CANDIDATE.md`](docs/architecture/PRODUCT_V1_ARCHITECTURE_CANDIDATE.md), Owner-approved under [`DEC-007`](docs/decisions/DEC-007-product-v1-implementation-start-authorization.md). ## Source Topology

```text
Source Topology: Multi Capability

Capabilities:
- Product
- Variant
- Option
- Option Value
- Image Role
- Image Assignment
- Content
```

`php-product` is one domain, so no `Domain` directory is used; `src/` holds one directory per capability, each containing only the responsibilities that capability actually owns, per the Package Building Standard §5. Every capability is split into a `Management/` side (`Command/`, `Criteria/`, `Service/`) and, when it has a consumer read, a `Consumer/` side (`Criteria/`, `Service/`); Image Role has a Management side only. The types both sides share stay at the capability level: the result DTOs (`DTO/`), `Enum/`, `Exception/`, `Repository/` (with `Repository/Pdo/`), and `ValueObject/`, together with internal shared support (`Product/Service/ProductConfigurationValidator`, `Content/Service/ContentLifecycle`, `Content/Mapper/ContentRecordMapper`). Classes live under `src/` with the PSR-4 prefix `Maatify\Product\`.

The capability list is the one enumerated by the Owner-approved architecture (§13). `src/` contains the seven capability directories (`Product`, `Variant`, `Option`, `OptionValue`, `ImageRole`, `ImageAssignment`, `Content`) plus the package-wide `Common`, `Exception`, and `Factory` responsibilities; no empty or ceremonial folder is created. `Content` owns the Content records of all three owners (Product, Option, Option Value), because they share one identity, lifecycle, and read contract (§3.5). The architecture allows capabilities to be merged or split "if the public contract and implementation justify" it (§13), so any change to this list is an approved change to this declaration, and code is placed according to it. The `*CriteriaDTO` types live in the `Criteria/` responsibility of their side; the shared PDO support lives in `Common/Repository/Pdo/`; and `Common/Command/CommandTextRules` holds the shared input-validation rules of Commands.

### Behavior and guarantees

- **Create.** `create()` writes an **inactive** Product and its single **active** empty-composition Variant in one local transaction; both rows exist or neither does. The Variant fingerprint is the SHA-256 of `v1`, its `display_order` is allocated through the shared `maatify/persistence` Ordering API under the Product row lock, and it has no SKU or barcode. The result carries both identities. The operation is not idempotent. It performs no Pricing, Inventory, or other cross-domain work.
- **Codes and keys.** `CreateProductCommand::$code`, Option and Option Value codes, and the Image Role key must be valid UTF-8, at most 100 characters, and not empty or whitespace only (any Unicode whitespace). They are stored exactly as supplied, never trimmed. Uniqueness uses the database collation `utf8mb4_unicode_ci` (the Product code in the package namespace, the Option code within its Product, the Value code within its Option, the role key in the role namespace), so `P-1` and `p-1` conflict, and a soft-deleted row keeps its code or key reserved; the only way back is the explicit restore.
- **Read.** `getById()` is the consumer read: it returns only an active, non-deleted Product, and any other identity raises `ProductNotFoundException`. `getByIdForManagement()` ignores status and filters only by soft-deletion state (`NON_DELETED` by default, `INCLUDE_DELETED`, `DELETED_ONLY`), matching `php-category`'s read pair; the same pair exists for Variants, Options, Option Values, Image Roles, and Image Assignments. DTO timestamps are `DateTimeImmutable` values hydrated in the Host Clock timezone, with no normalization, and serialize as `DATE_ATOM`; every DTO rejects a non-positive identity.
- **Variant reads.** `getById()` and `listByProductId()` return only consumer-visible Variants: the Variant and its Product are active and not deleted, every selected Option and Option Value is active, not deleted, and has a non-deleted label, the composition covers exactly the Product's active Options (none missing, none extra), and the Product's configuration is valid as a whole: every active Value of an active Option is represented by at least one active, structurally valid Variant. When that product-wide rule is broken (possible only through direct SQL, because no package write path breaks it), **every** Variant of the Product is hidden from the single get and from the list alike, so the two reads never disagree; management reads keep showing the stored state; and the reads return the correct result again as soon as every active Value is represented (proven by `tests/Integration/Runtime/VariantReadTest.php`). `getByIdForManagement()` and `listByProductIdForManagement()` ignore visibility and filter by status (`null` means any) and soft-deletion state. A missing or not-visible identity raises `VariantNotFoundException`; a list read never fails for a missing Product and returns an empty collection. Lists are ordered by `display_order, id` and bounded to at most 100 (`maxResults` 1 to 100). `VariantDTO` carries `id`, `productId`, `sku`, `barcode`, `status`, `displayOrder`, `composition` (the Option and Option Value pairs ordered by numeric Option identity, empty for a simple Product's Variant), and the three timestamps; the composition fingerprint is internal and never exposed. Every identity argument must be a positive integer, otherwise `ProductInvalidArgumentException`.
- **Composition resolution** (`resolveByComposition()`, consumer read, read-only). The selection is a `VariantCompositionCriteriaDTO` of `OptionValueSelection` pairs in any order; it is canonicalized by numeric Option identity, and an empty selection is valid. The failure classes: a Product that does not exist or is not consumer-visible (inactive or soft deleted) raises `ProductNotFoundException`, judged before the selection. A structurally invalid selection raises `ProductInvalidArgumentException`: a repeated Option (raised by the criteria at construction), an Option that is not an active, non-deleted Option of the Product (including an Option of another Product or an unknown identity), a Value that is not an active, non-deleted Value of the selected Option (including a Value of another Product or paired with the wrong Option), and incomplete coverage (an active Option left unselected; so a non-empty selection on a simple Product and an empty selection on a configurable Product are both rejected). A structurally valid, complete selection that matches no consumer-visible Variant raises `VariantNotFoundException`, including a historical inactive composition and a match hidden by the product-wide rule; the match is looked up by fingerprint among the Product's active, non-deleted Variants and confirmed against the actual pairs, and a fingerprint that matches with different pairs raises `ProductPersistenceException`. It never creates a Variant, never reactivates one, and never invents a default. Proven by `tests/Integration/Runtime/VariantResolutionTest.php`.
- **Lifecycle contract** (every family). `updateStatus()`, `softDelete()`, and `restore()` exist for Products, Variants, Options, Option Values, and Image Roles (for the Option and Value `updateStatus()`, see *Option and Value status*); `softDelete()` and `restore()` for Image Assignments, which have no status. A missing identity raises the family's not-found exception; a non-positive identity raises `ProductInvalidArgumentException`. A soft-deleted row accepts nothing but `restore()`: a status change, a re-delete, a default operation, or any other change raises `ProductBusinessRuleException`. A child under a soft-deleted owner cannot be created or changed until the owner chain is restored: an Option or Variant of a deleted Product, a Value of a deleted Option or Product, an Image Assignment of a deleted Product or target Variant (`ProductBusinessRuleException`); `clearDefault()` is the one exception, see the Image Assignments bullet. `restore()` requires the row to be soft deleted and its owner chain not deleted, preserves the saved status (an inactive row stays inactive), places an ordered row at the end of its scope (see Restore position), and revalidates the Product invariants before writing; a rejected restore leaves the row deleted. Deactivating or deleting a parent never changes a child. Inactivity alone blocks no management operation. A request for the current status changes nothing (no write, `updated_at` unchanged). Product activation requires a non-empty name in a non-deleted Product Content record and a valid configuration (`INV-01` to `INV-06`); Product deactivation needs nothing. A Variant is activated only when its full composition satisfies the current configuration (`INV-09`), and deactivating or deleting it is rejected when the Product would be left without a valid active Variant or a Value would be left unrepresented (`INV-01`, `INV-04`, `INV-07`); such changes belong to reconfiguration. An Option or Value that is part of the active configuration cannot be soft deleted outside reconfiguration, because an active Variant would select a deleted member. Every validation runs on the whole Product graph read under the Product lock. Proven by `tests/Integration/Runtime/ProductLifecycleTest.php`, `VariantLifecycleTest.php`, and `OptionLifecycleTest.php`.
- **Options and Values.** `create()` writes an **inactive** Option under a non-deleted Product (or an inactive Value under a non-deleted Option of a non-deleted Product) with its position from the shared Ordering API within its owner scope, under the Product lock. A duplicate code raises `OptionCodeAlreadyExistsException` or `OptionValueCodeAlreadyExistsException` (MySQL driver error 1062, original `PDOException` as `previous`). A missing owner raises `ProductNotFoundException` or `OptionNotFoundException`; a soft-deleted owner raises `ProductBusinessRuleException`. Their labels are Option and Option Value Content records (see Content).
- **Option and Value status** (`OPT-02`, `OVL-02`). `updateStatus()` on the Option and Option Value Management services changes the status of one non-deleted row. It runs in the savepoint transaction runner and locks the Product's whole configuration graph (`lockSnapshot`) before checking anything. A non-positive identity raises `ProductInvalidArgumentException`; a missing identity raises `OptionNotFoundException` or `OptionValueNotFoundException`; a soft-deleted row, or a soft-deleted owner (the Product, or for a Value its Option), raises `ProductBusinessRuleException`. A request for the current status changes nothing (no write, `updated_at` unchanged). Otherwise the whole configuration is validated with the new status by the same validator as every other mutation, and a result that breaks `INV-01` to `INV-07` raises `ProductBusinessRuleException` with nothing written; on success only `status` and `updated_at` change. So a Value of an inactive Option, or an Option outside an active configuration, can change freely, while deactivating an Option or Value that an active Variant selects, activating an Option that the active Variants do not cover, or activating a Value of an active Option that no active Variant represents is rejected; `reconfigure()` remains the way to change the active set atomically. Proven by `tests/Integration/Runtime/OptionStatusTest.php`.
- **Reconfiguration** (`reconfigure()`, management command). The command is the complete target state: the set of Options that must be active with each one's complete set of active Values, and the set of Variant compositions that must be active. Options and Values must exist under the Product, be non-deleted, and be labelled; the operation activates and deactivates them, it never creates them, and it carries no SKU or barcode (new Variants start with `NULL`, `VAR-01` owns them). Every target composition must select exactly the target Options with target Values, no composition may repeat, every target Value must be represented by at least one target Variant, and at least one Variant is required; an empty composition is valid only for a simple target (no Options), and a simple target allows no other composition. An active Variant absent from the target becomes **inactive** and keeps its identity and history. A target composition that already exists in the Product's history (active, inactive, or soft deleted) must name that Variant through `reuseVariantId`, otherwise `VariantCompositionConflictException` identifying the existing Variant; a named Variant that does not carry the composition, carries another composition, or belongs to another Product is also `VariantCompositionConflictException`, and an unknown reuse identity is `VariantNotFoundException`. The match is confirmed against the actual pairs, and a fingerprint that matches with different pairs is `ProductPersistenceException`. A reused inactive Variant is reactivated; a reused soft-deleted Variant is restored and activated inside the same operation, at the end of its Product's order; a reused active Variant is unchanged. A new composition becomes a new **active** Variant with its position from the Ordering API. The transition to a simple Product requires the original empty-composition Variant to be named for reuse; when no empty-composition Variant exists in the Product's history, the operation fails closed with `ProductPersistenceException` and never creates a second one (`INV-10`). Options outside the target set are deactivated and their Values are retained unchanged as history; Values of a target Option that are not listed are deactivated. A target that would violate an invariant (an Option or Value of another Product, a deleted or unlabelled Option or Value, incomplete or extra coverage, an unrepresented Value, no Variant, an empty composition in a configurable target or a non-empty one in a simple target) raises `ProductBusinessRuleException`; a repeated Option, Value, composition, or reuse identity in the command raises `ProductInvalidArgumentException` at construction; a missing Product raises `ProductNotFoundException` and a soft-deleted one `ProductBusinessRuleException`. The result lists the Variant identities created (in request order), reactivated, restored, and deactivated, and the Option and Value identities activated and deactivated (ascending); a reused Variant that was already active appears in no list. Every failure rejects the whole operation: nothing is written. Proven by `tests/Integration/Runtime/ProductReconfigurationTest.php` and `ConcurrentReconfigurationTest.php`.
- **Image Roles.** `create()` writes an **active** Role; a duplicate key raises `ImageRoleKeyAlreadyExistsException`. Role IDs are a Product-owned namespace, never Category Image Role IDs. Changing a Role's status or deleting it never changes an assignment.
- **Image Assignments.** `create()` assigns a Media Asset to a non-deleted Product (`variantId` null) or to a non-deleted Variant of that Product within an exact `(roleId, languageCode, platform)` scope, where `NULL` is an exact value. A Variant of another Product raises `ProductInvalidArgumentException`; a missing Product, Variant, or Role raises its not-found exception; a soft-deleted Product or Variant, or a Role that is inactive or soft deleted, raises `ProductBusinessRuleException`. The identity `(target, mediaAssetId, roleId, languageCode, platform)` is unique across soft-deleted history under the collation (`ImageAssignmentAlreadyExistsException`, naming the identity; restore is the way back). A new assignment is not the default and takes its position within its exact scope from the shared Ordering API over the generated `ordering_scope` column; the package computes the same key, and an Integration test asserts it equals the stored generated value. `setDefault()` makes a non-deleted assignment the single default of its exact scope, clearing the previous default of that scope in the same transaction, with the database unique key on the default scope as the final guard; it requires a non-deleted target Product and Variant and a non-deleted Role when one is set, while an inactive Product, Variant, or Role does not block it; the current default is a no-op. `clearDefault()` removes the marker of a non-deleted assignment even when its target or Role is soft deleted, promotes nothing, and is a no-op for a non-default; on a soft-deleted assignment it is rejected like every other change. `softDelete()` clears the marker and promotes nothing; `restore()` always leaves the row non-default; a soft-deleted assignment can never become default. `restoreAsDefault()` (`IAS-07`) restores a soft-deleted assignment and makes it the default of its exact scope in one update that clears `deleted_at`, sets `is_default`, places the row at the end of its live scope, and stamps `updated_at` from the Clock. It locks like `setDefault()` (Product, target Variant when set, Role when set, then the assignment) and has its preconditions: a non-soft-deleted assignment is `ProductBusinessRuleException`, as for `restore()`, and so is a soft-deleted target Product or Variant or a soft-deleted Role, while an inactive Product, Variant, or Role does not block it. It never replaces a default: when the exact scope already has a live default, read under those locks, it raises `ImageAssignmentDefaultConflictException` naming the assignment and the live default, and writes nothing. The database unique key on the default scope is the final guard: only MySQL driver error 1062 on `uq_maa_product_image_assignments_default_scope` becomes that exception, with the original `PDOException` as `previous`; any other error propagates unchanged. The package never resolves or verifies the Media Asset. Proven by `tests/Integration/Runtime/ImageAssignmentCommandTest.php`, `RestoreAsDefaultTest.php`, and `ConcurrentDefaultReplacementTest.php`.
- **Management lists, search, and pagination.** Every management list has an unpaginated read bounded by its criteria's `maxResults` (1 to 100, default 100; the result is silently truncated at the bound, with no "more" flag) and a paginated twin through `maatify/persistence` (`PdoPaginator`, `PageRequest` in, `PageResult` of the family's public DTO out): 20 per page by default, 1 to 100 (a larger request is clamped), each list's sort whitelist with an unknown key falling back to its default, and `id` ascending as the tie-breaker; `maxResults` does not apply to a page. Products: `listForManagement()`/`paginateForManagement()`, by `id` (sort keys `id`, `code`, `created_at`, `updated_at`). Variants: `listByProductIdForManagement()`/`paginateByProductIdForManagement()`; Options: `listByProductIdForManagement()`/`paginateByProductIdForManagement()`; Option Values: `listByOptionIdForManagement()`/`paginateByOptionIdForManagement()`; each by `display_order, id` (sort keys `display_order`, `id`, `created_at`, `updated_at`). Image Roles: `listForManagement()`/`paginateForManagement()`, by the binary value of the role key then `id` (sort keys `role_key`, `id`, `created_at`, `updated_at`). Image Assignments: by `ordering_scope`, `display_order`, `id`; the page sorts by the derived `business_order`, `ROW_NUMBER() OVER (ORDER BY ordering_scope, display_order, id)` over the same filtered rows (sort keys `business_order`, `id`, `created_at`, `updated_at`), as in `php-category`. Filters are the family's status (`null` means any) and the deleted state (`NON_DELETED` by default); management lists hide nothing for an owner's state, a non-positive owner identity is `ProductInvalidArgumentException`, and a missing owner yields an empty result. `total`, `filtered`, and the page use one filter, except the Product search. Every unpaginated `LIMIT` is bound as an integer parameter. **Search** exists for Products only: `ProductListCriteriaDTO::$search` is trimmed of Unicode whitespace, must then be non-empty and at most 100 characters, and matches a literal substring of `code` (`!`, `%`, and `_` are escaped with `!`; `LIKE ... ESCAPE '!'`, which works under any Host `sql_mode`, including `NO_BACKSLASH_ESCAPES`; `\` is an ordinary character) under the collation; `total` counts without it and `filtered` and the page with it. **Business-key reads:** `getByCodeForManagement()` and `getByKeyForManagement()` find a Product by `code` or a Role by key under the collation, with the identifier rules of creation and the deleted-state filter, raising `ProductNotFoundException` or `ImageRoleNotFoundException` naming the value. There is no read by SKU, barcode, or Option or Value code in V1. No counts, aggregates, or summaries beyond the pagination metadata are provided. Proven by `tests/Integration/Runtime/ManagementListTest.php`.
- **Image Assignment criteria.** `ImageAssignmentListCriteriaDTO` lists the assignments of one Product. `ImageAssignmentTargetFilter` selects any target, the Product level only (`variant_id IS NULL`), or one Variant; `ImageAssignmentRoleFilter` (by Role identity, as in `php-category`), `ImageAssignmentLanguageFilter`, and `ImageAssignmentPlatformFilter` each select omitted (no condition), exactly `NULL`, or one exact value compared under the collation, with the creation rules for language and platform. Omitting a dimension and asking for `NULL` are different typed states; `NULL` never acts as a wildcard and a value never matches `NULL`.
- **Consumer reads of Options, Values, and Image Assignments** (`OPT-R2`, `OVL-R2`, `IAS-R2`). `listVisibleByProductId()` returns the active, non-deleted, labelled Options of a Product that has at least one consumer-visible Variant, and `listVisibleByOptionId()` the active, non-deleted, labelled Values of such an Option (itself active, non-deleted, and labelled) that are represented by at least one consumer-visible Variant. Consumer Variant visibility has one SQL source shared with the Variant reads, so the product-wide rule of the Variant reads applies: while an active Value of an active Option is represented by no active valid Variant, every Option and Value of the Product is hidden, and they return as soon as the configuration is valid again. A missing, inactive, deleted, or simple Product yields an empty collection. `listVisibleByExactScope()` reads one exact image scope (`ImageAssignmentExactScopeCriteriaDTO`): the Product level when `variantId` is `null`, otherwise one Variant of that Product, with the exact role, language, and platform, where `null` is exactly `NULL` and strings compare under the collation; nothing is inherited between the Product and Variant levels (A§9.4). An assignment is returned only when it is not deleted, its Product is active and not deleted, its target Variant is active and not deleted, and its Role, when set, is active and not deleted. All three order by `display_order, id`, return at most `maxResults` (1 to 100, bound as an integer), and raise `ProductInvalidArgumentException` for a non-positive identity or an invalid scope string; otherwise they never fail and return an empty collection. They never resolve a Media Asset, never choose a default (`isDefault` is returned as stored), and never fall back. Proven by `tests/Integration/Runtime/ConsumerReadTest.php`.
- **Ordering** (`VAR-05`, `OPT-05`, `OVL-05`, `IAS-06`). `updateDisplayOrder()` on the Variant, Option, Option Value, and Image Assignment services moves one non-deleted row within its scope: a Variant or an Option within its Product, a Value within its Option, an assignment within its exact `(target, role, language, platform)` scope (the generated `ordering_scope` key, where `NULL` is an exact value). It runs in the savepoint transaction runner, locks the Product first and then the owner chain in the stable order (for an assignment: Product, target Variant when set, then the assignment), and delegates the move to `ScopedOrderingManager::moveWithinScope()` from `maatify/persistence`, which participates in the open transaction, locks the scope, clamps a position above the current maximum to it, leaves a row already at the position unchanged (no write), shifts the other live rows of that scope only, and stamps the moved row's `updated_at`; the package has no shifting SQL or ordering engine of its own. A position below 1 or a non-positive identity is `ProductInvalidArgumentException` at construction; a missing identity is the family's not-found exception (as is a `false` from the shared API); the row or any owner soft deleted is `ProductBusinessRuleException`. Ordering never changes the configuration's validity, so no invariant is revalidated. Proven by `tests/Integration/Runtime/OrderingCommandTest.php`, including composition with a Host transaction that rolls the move back.
- **Restore position.** Restoring an ordered row (Option, Option Value, Variant, Image Assignment, including a Variant that `reconfigure()` restores for reuse) places it at the end of its live scope: its `display_order` becomes the shared Ordering API's next position (`getNextPosition()`), computed under the operation's locks and written in the same update that clears `deleted_at`. Soft deletion does not compact positions. The reason: `getNextPosition()` ignores soft-deleted rows, so a new row may already hold the deleted row's old position, and keeping it on restore could duplicate a live position and break the shifting of `moveWithinScope()`. This deliberately differs from `php-category`, which keeps the original position.
- **Variant identifiers** (`VAR-01`). `updateIdentifiers()` changes the optional SKU and barcode of a non-deleted Variant of a non-deleted Product; each field is independently `VariantIdentifierChange::unchanged()`, `set($value)`, or `clear()`. A set value is valid UTF-8, not empty or whitespace only (any Unicode whitespace), at most 128 characters, and stored verbatim (a barcode keeps its leading zeroes); a violation is `ProductInvalidArgumentException` at construction. The Product row is locked first (with the configuration graph in the stable order), then the Variant row is read under its lock. A missing Variant raises `VariantNotFoundException`; a soft-deleted Variant or Product raises `ProductBusinessRuleException`; an inactive Variant or Product blocks nothing. A field set to its exact stored value, or cleared while `NULL`, does not change, and when no field changes nothing is written. Each value is unique across all Variants under the collation while assigned, so case variants collide and a soft-deleted Variant keeps its values reserved; replacing or clearing releases the old value. Only MySQL driver error 1062 on `uq_maa_product_variants_sku` or `uq_maa_product_variants_barcode` becomes `VariantSkuAlreadyExistsException` or `VariantBarcodeAlreadyExistsException`, naming the value, with the original `PDOException` as `previous`; there is no pre-check. The Variant identity never changes. Proven by `tests/Integration/Runtime/VariantIdentifiersTest.php`.
- **Content** (`CNT-01` to `CNT-04`, `CNT-R1`, `CNT-R2`). A Management and a Consumer service per owner (`ProductContentManagementServiceInterface` and `ProductContentConsumerServiceInterface`, `OptionContentManagementServiceInterface` and `OptionContentConsumerServiceInterface`, `OptionValueContentManagementServiceInterface` and `OptionValueContentConsumerServiceInterface`). A record's identity is `(owner, languageCode)`, where `null` is the single unlocalized record; it is immutable and unique across soft-deleted history under the collation, so `EN` and `en` conflict and a deleted identity is brought back only by `restore()`. `create()` locks the owner's Product configuration, raises the owner's not-found exception (`ProductNotFoundException`, `OptionNotFoundException`, `OptionValueNotFoundException`) for a missing owner and `ProductBusinessRuleException` when the owner or an ancestor is soft deleted (an inactive owner blocks nothing), and maps only MySQL driver error 1062 on the identity key to `ProductContentAlreadyExistsException`, `OptionContentAlreadyExistsException`, or `OptionValueContentAlreadyExistsException` with the original `PDOException` as `previous`; there is no pre-check and no implicit restore. `update()` replaces every field of a non-deleted record by its identity and writes nothing when the fields equal the stored ones. `softDelete()` is rejected when it would remove the last non-deleted name of an active Product (`INV-06`) or the last non-deleted label of an active Option or of an active Value of an active Option (`INV-05`), validated on the locked configuration graph; an inactive owner may lose its last label. `restore()` requires a soft-deleted record and a live owner chain and revalidates the invariants. A soft-deleted record accepts nothing but `restore()`, and no record of a soft-deleted owner chain can be changed. A missing record raises `ProductContentNotFoundException`, `OptionContentNotFoundException`, or `OptionValueContentNotFoundException`. Management reads take a `ContentLanguageFilter` (exact language, unlocalized only, or all languages) and a deleted-state filter, order by `language_code` (the unlocalized record first) then `id`, list at most `maxResults` (1 to 100), and paginate through `maatify/persistence` (`PageRequest`/`PageResult`, 20 per page by default, 1 to 100, sortable by `language_code`, `id`, `created_at`, or `updated_at`, ties by `id`). The consumer read `listVisible()` takes an `ExactContentLanguage` (exact language or unlocalized only) and returns zero or one record: not deleted, under an active, non-deleted Product, and for Option and Value Content an active, non-deleted Option (and Value); otherwise an empty collection. Exact matching never falls back: `ar` never returns the unlocalized record and the unlocalized selector never returns a localized one. Proven by `tests/Integration/Runtime/ContentCommandTest.php`.
- **Identity stability.** Enforced by the application contract (architecture §4.1, §11.1), not by triggers, and the three layers are distinct. *Schema:* uniqueness of each identity (including soft-deleted history), restricted foreign keys, no triggers or routines; the database does not stop an `UPDATE` of an identity column issued outside the package. *Application:* no package write path updates `id`, `code`, or any other identity column, and no service method replaces one. *Tests:* `tests/Unit/IdentityStabilityTest.php` scans every `UPDATE ... SET ... WHERE` statement in `src/`, whatever form its table name takes in the source (a literal, a class constant, or a concatenated expression), rejects any assignment of an identity column (`id`, `code`, `role_key`, `composition_fingerprint`, the owner and target keys, `language_code`, `platform`, `media_asset_id`, `role_id`, and the generated identity and scope keys), asserts that the number of statements scanned equals the number of `UPDATE` statements present, so none escapes, and proves with fixed negative cases that an identity assignment is rejected in each table-name form. It also checks every service interface for an identity-replacing method. It cannot see writes made by the Host outside the package, and a schema test asserts that no trigger or routine exists. Corrections use an explicit migration or replacement process outside the package.
- **Transactions.** The package never commits or rolls back a transaction it did not start. Every mutation runs through `PdoSavepointTransactionRunner` (`maatify/persistence` `^1.4`): it owns and commits a transaction when none is active, and when the Host already has an active transaction on the same PDO connection it runs inside an operation-local savepoint in it, so the Host still decides commit or rollback of its own transaction. Atomic composition requires every participant to use that one connection. Proven against real MySQL inside a caller-owned transaction: `tests/Integration/Runtime/HostTransactionAtomicityTest.php` for Product creation, and `HostTransactionSavepointTest.php` for Content create and soft delete, `setDefault()` (including the previous default it had already cleared), and Variant `updateStatus()` and `updateIdentifiers()`; each failed operation leaves none of its writes, the Host transaction stays active, and the Host's other work is kept.
- **Locking.** Every mutation that can affect a Product's graph takes the Product row lock (`SELECT ... FOR UPDATE`) before reading any state it validates, then locks, in this stable order, the Product's Options, Option Values, and Variants (ascending identity within each table) when it reads the configuration, and the Image Role and Image Assignment rows it touches (Product, Variant, Role, Assignment); a Content mutation locks the owner's configuration the same way and then its Content row. The configuration graph is read with locking reads only, so it reflects the latest committed state even inside a Host transaction that established an earlier consistent-read snapshot. Validation runs on that graph in memory before any write. `tests/Integration/Runtime/LockingReadSnapshotTest.php` proves the locking reads for two cases (Product activation and Variant deactivation inside a Host transaction that holds an older snapshot see a change committed elsewhere).
- **Failure contract.** A duplicate identity (MySQL driver error 1062 on a unique key the package owns) becomes the family's conflict exception, with the original `PDOException` as `previous`; where a statement can violate more than one key (Variant SKU and barcode) or a key is matched by name (Content), the violated key is read only from the trailing `for key '...'` clause of the driver message and compared by equality, never from the duplicated value. A storage value the package cannot interpret, or stored state that is inconsistent (a composition fingerprint that does not match its pairs, a missing original empty-composition Variant during the transition to simple), raises the public, package-owned `ProductPersistenceException` (a `maatify/exceptions` `SystemMaatifyException` that implements `ProductExceptionInterface`). It reports a broken storage contract, not a caller error, so it is not retryable by the caller, and it carries no Product data. Inside a mutation it is raised within the operation's transaction or savepoint, so the failed operation is rolled back like any other failure. `ProductBusinessRuleException` (a `BusinessRuleMaatifyException`) is the `FC-INV` class for every lifecycle precondition and invariant failure. **Every other `PDOException` and `Throwable` propagates unchanged**; nothing is swallowed or blanket-wrapped. When the package started the transaction, it is rolled back before the exception propagates. When the Host already had a transaction on the connection, the failed operation is rolled back to its savepoint before the exception propagates: none of its writes remain in the Host transaction, so a Host that catches the exception and still commits cannot persist a partial operation. The package never commits or rolls back the Host transaction. After a statement-level failure the Host transaction stays active and the Host's other work in it is unaffected. A failure that makes MySQL roll back the whole transaction, such as a deadlock (driver error 1213), ends the Host transaction on the server, including the Host's earlier work in it; the package propagates that `PDOException` unchanged, and the Host must treat it as a failure of its whole transaction. `tests/Integration/Runtime/DeadlockPropagationTest.php` proves one deadlock shape: two Host transactions lock two Product rows in opposite orders and the package call loses.
- **Timestamps.** `created_at`, `updated_at`, and `deleted_at` are taken from the Host-injected `ClockInterface` and stored as the `Y-m-d H:i:s` string of that instant. Reads return `DateTimeImmutable` values hydrated in the Host Clock's timezone. The package performs no timezone normalization and makes no UTC claim. Proven by `tests/Integration/Runtime/ClockTimestampTest.php` for Products, Variants, Options, Image Assignments, and Content: the stored value is the Clock's instant and the returned value is hydrated in the reading Clock's timezone.
- **Concurrency.** Product creation serializes on the database unique key for the code and on the Product row lock for the Variant: concurrent creates of one code yield exactly one Product, and concurrent creates of different codes each yield exactly one Variant. Concurrent reconfigurations of one Product serialize on the Product row lock: identical target sets yield one winner and typed conflicts for the rest (never a duplicate-key error), and different target sets leave exactly one valid committed configuration with at most one identity per composition. Concurrent default replacements within one exact scope leave exactly one default, and concurrent restores as default of two soft-deleted assignments of one exact scope yield one winner and an `ImageAssignmentDefaultConflictException` for the other, with exactly one default left. `tests/Integration/Runtime/ConcurrentMutationTest.php` covers further races: concurrent deactivations of two Variants that are each dispensable but not both leave one winner and one `ProductBusinessRuleException`; concurrent moves within one Product keep positions unique and contiguous; concurrent activation and deletion of the only name never leave an active Product without a name; one SKU set on two Variants yields one winner and one typed conflict; and `setDefault()` against `create()` on one Role across Products never deadlocks. All proven against real MySQL with separate processes and connections, released together and repeated in rounds, by `tests/Integration/Runtime/ConcurrentCreationTest.php`, `ConcurrentReconfigurationTest.php`, `ConcurrentDefaultReplacementTest.php`, and `ConcurrentMutationTest.php`.

| Entity | Has `status` | Soft-deletable | Default at creation |
|---|---|---|---|
| Product | yes | yes | `inactive` (A§6.1) |
| Variant | yes | yes | The initial empty-composition Variant is `active`. Non-empty Variants are created only by reconfiguration as active members of the validated set (A§4.5). |
| Option | yes | yes | `inactive` |
| Option Value | yes | yes | `inactive` |
| Image Role | yes | yes | `active` |
| Content (three tables) | no | yes | n/a |
| Image Assignment | no (`is_default` only) | yes | not default (see 3.7) |
| Variant composition pair | no | no. It has no independent update, delete, or restore lifecycle (A§11.3). | n/a |

- Status values are exactly lowercase `active` and `inactive`. Public mutations take a typed enum. The database must reject other casings (A§6.1, A§11.3).
- `status` and `deleted_at` are independent dimensions. `deleted_at IS NULL` means not soft-deleted. Runtime hard delete is not used (A§6.1).
- **No cascade.** Deactivating or deleting a parent never changes a child's `status` or `deleted_at`. A parent that is inactive or deleted only suppresses the child's consumer visibility (A§6.1).
- **Restore** reuses the original identity and preserves the saved `status`. Restoring an `inactive` row never activates it. Restore must revalidate both entity-level and aggregate invariants, and is rejected if they fail (A§6.1, A§6.5). A restored ordered row takes the end of its live scope (see 1.4). This applies to Products, Variants, Options, Option Values, Image Roles, and Image Assignments.
- **Re-adding a soft-deleted identity.** Create never restores implicitly and never inserts a second row: it fails with a typed conflict that identifies the colliding identity, and the only way back is the explicit restore, which reuses the original identity and revalidates the invariants. This applies to every family that keeps identity across soft-deleted history: Product `code`, Option and Option Value codes, the Role key, Content identity, Variant composition, Variant SKU and barcode, and Image Assignment identity, each with its typed `FC-CONF` exception (proven by Integration tests). This is A§6.1, A§9.3, A§6.4, and A§17, and matches A§5.3 and `php-category`.
- **Lifecycle rules under soft deletion.** Any change to a soft-deleted row other than the explicit `restore` is rejected with `FC-INV`: no status change, reorder, content change, default operation, or re-delete stands in for restore. Creating or changing a child under a soft-deleted owner (an Option or Variant of a deleted Product, a Value of a deleted Option, an Image Assignment of a deleted Product or target Variant) is rejected with `FC-INV`; the owner chain is restored first. `restore` preserves the saved status, requires the owner chain not to be deleted, and revalidates the invariants before completing. `FC-NF` is for an identity that does not exist; `FC-INV` is for a row that exists but whose state, or whose owner's state, prevents the operation. An `inactive` status alone blocks no management operation and no data preparation; what blocks an operation is this lifecycle contract and the invariants the operation would break.
- Content records (all three owners) follow the same lifecycle: a soft-deleted record accepts only `restore()`, and a record of a soft-deleted owner chain cannot be created or changed.
- A soft-deleted Image Assignment is never the default: soft deletion clears the marker, restore leaves the row non-default, restore-as-default clears `deleted_at` and sets the marker in the same update, and the database rejects a soft-deleted default row. The `CHECK` is the final database guard (A§11.1); the operations that maintain the rule are `IAS-02` to `IAS-05` and `IAS-07`.
- No identity-correction API exists in V1. `id` and `code` are never updated (A§4.1). Corrections use an explicit migration or replacement process outside this package.

#### 1.3 Timestamps and the clock

`created_at`, `updated_at`, and `deleted_at` are assigned by the application from the Host-injected `ClockInterface` (`maatify/shared-common`). There is no database timestamp default or `ON UPDATE`. The package performs no timezone normalization and must not claim UTC (A§10, A§11.3). Public timestamps are `DateTimeImmutable` values hydrated in the Host Clock timezone and serialized as `DATE_ATOM`, the same representation as `php-category`. This applies to every DTO.

#### 1.4 Ordering

Entities with persistent ordering: Option (scope: Product), Option Value (scope: Option), Variant (scope: Product), Image Assignment (scope: target plus role, language, and platform). `Product` has none (DEC-006).

- Positions are positive and managed by the shared `maatify/persistence` Ordering API (`ScopedOrderingManager`), not by database defaults and not by a package-local engine (A§11.3, Package Building §11, §16).
- Create Commands do not accept a position. A new row gets its position through the Ordering API.
- Movement is a dedicated typed ordering command per entity (`updateDisplayOrder()` for Variants, Options, Option Values, and Image Assignments). The repository returns `bool` from `moveWithinScope()`, and the service turns `false` into a not-found failure (Package Building §10, §16).
- A target above the current maximum is clamped to the maximum by the shared API. A non-positive target is rejected before clamping (persistence reference). The Command must reject a non-positive position itself (`FC-VAL`).
- Every list whose entity has persistent ordering ends with `display_order, id` (A§12). Content lists are ordered by `language_code` (the unlocalized record first) then `id`. Products are listed by `id` and Image Roles by the binary value of the role key then `id`.
- The multi-dimensional Image Assignment scope maps onto the shared API's single scope column through the generated `ordering_scope` key; the package computes the same key and an Integration test asserts equality with the stored value. A restored row takes the next position of its live scope, at the end: `getNextPosition()` ignores soft-deleted rows, so the old position may be held by a newer row, and keeping it could duplicate a live position and break `moveWithinScope()`. Soft deletion does not compact positions. This deliberately differs from `php-category`, which keeps the original position.

#### 1.5 Pagination and list bounds

- Every **unpaginated** consumer or management list returns at most 100 records (A§12).
- Large management lists use `maatify/persistence` `PageRequest` and `PageResult`. A package-local pagination engine is forbidden (A§12, Package Building §11).
- The package owns the query semantics: searchable fields, filters, matching, count alignment, and the result contract. The shared package owns only the pagination mechanics (Package Building §11).
- **Every management list** has an unpaginated read bounded by `maxResults` (1 to 100, default 100, silently truncated) and a paginated twin through `PdoPaginator` (20 per page by default, 1 to 100, `id` ascending as the tie-breaker). Consumer lists stay unpaginated and bounded to 100. Search exists for Products only (a literal substring of `code`). See *Management lists, search, and pagination* in Behavior and guarantees.
- **Content.** The management Content list is bounded by `maxResults` (1 to 100, default 100). The paginated management Content read uses `PdoPaginator` with 20 records per page by default, 1 to 100, the sort whitelist `language_code` (default, ascending), `id`, `created_at`, `updated_at`, and `id` ascending as the tie-breaker; the total and filtered counts use the same filter as the data, and `maxResults` does not apply to it.

#### 1.6 Exact scope and `NULL`

`NULL` is an exact value, never a wildcard, fallback, "all", or "default" (A§9.3, A§12, Package Building §24).

- **Content** language: three mutually exclusive selectors (exact language, unlocalized only, all languages). "No language filter" and "`NULL`" must not be the same parameter (A§12). Typed as `ContentLanguageFilter` (management) and `ExactContentLanguage` (consumer, without the all-languages state).
- **Image assignment** role, language, and platform: each dimension is matched exactly. `NULL` means exactly `NULL`. Non-`NULL` strings compare under `utf8mb4_unicode_ci`. There is no fallback (A§9.3).
- No Product-level fallback for Variant-level assignments, and no Variant-level substitution for Product-level assignments (A§9.4).
- Management criteria for image-assignment dimensions distinguish omitted, exactly `NULL`, and one exact value per dimension (`ImageAssignmentTargetFilter`, `ImageAssignmentRoleFilter`, `ImageAssignmentLanguageFilter`, `ImageAssignmentPlatformFilter`).

#### 1.7 Atomicity, locking, and transactions

- Every multi-table Product mutation is atomic locally (A§14). The package never claims cross-domain atomicity. Pricing, Inventory, Supplier, and fulfilment reconciliation belongs to the Host/Catalog coordinator (A§5.4, A§14).
- Any mutation that can affect Product content validity, Option/Value activation, Variant composition or status, or configuration serializes on the **Product row** before it reads current state (A§6.4, A§11.6). Read-before-write without locking and database uniqueness is not sufficient.
- Image default replacement locks the owning target scope and uses the database unique key as the final guard (A§9.4, A§11.4). Lock order across Product, Variant, Role, and Assignment rows must be stable (A§11.6).
- The package must not commit or roll back an outer transaction it does not own (A§11.6, A§14). It cooperates with the shared transaction contract. No automatic retry is claimed, because the sources permit retry only where the shared contract explicitly allows it (A§11.6).
- Duplicate identity is blocked by database-enforced keys. Application pre-checks are advisory (A§9.4, A§11.1).
- **Every mutation** runs through `PdoSavepointTransactionRunner` (`maatify/persistence` `^1.4`). It owns and commits a transaction when none is active. Inside a Host transaction on the same connection it runs in an operation-local savepoint, rolls back to it on failure, and never commits or rolls back the Host transaction, so a failed call leaves none of its writes behind. This keeps the Host transaction usable only after a statement-level failure: when MySQL itself rolls back the whole transaction, such as on a deadlock (driver error 1213), the Host transaction and its earlier work are gone, the `PDOException` propagates unchanged, and the Host must treat it as a failure of its whole transaction (see Failure contract).
- **Lock order.** For every multi-table mutation: the Product row first, then Options in ascending `id`, then Option Values, then Variants, then Image Roles, then Image Assignments, ascending `id` within each group. The state a mutation builds on is read only after the Product lock is taken, with locking reads.

### 2. Structural Invariants

These are postconditions of every committed mutation, including while a Product is `inactive`. Inactivity is not permission to commit a broken graph (A§6.2, A§6.5).

| ID | Invariant | Basis |
|---|---|---|
| `INV-01` | A Product is exactly one of two forms. **Simple:** no active Options and exactly one active, non-deleted, empty-composition Variant, with no active non-empty Variant. **Configurable:** at least one active Option and at least one active, non-deleted Variant. | A§4.3, A§4.4, A§6.2 |
| `INV-02` | Every active Variant has exactly one active Value for every active Option, no Value of an inactive or deleted Option, and no missing or extra Option. | A§4.4, A§6.3 |
| `INV-03` | Each selected Option and Value belongs to the same Product. Each Value belongs to its selected Option. This is enforced by composite foreign keys, not only by application code. | A§4.4, A§11.1 |
| `INV-04` | Every active Option has at least one active, non-deleted Value. Every active Value of an active Option appears in at least one active valid Variant. | A§6.2 |
| `INV-05` | Every active Option and every active Value of an active Option has a non-empty label in at least one non-deleted Content record. | A§5.4, A§6.3 |
| `INV-06` | While `Product.status = active`, the Product has at least one non-deleted Product Content record with a non-empty `name`. | A§6.2, A§6.5 |
| `INV-07` | No mutation may deactivate or delete the last valid active Variant, remove the last usable Product name from an active Product, or remove a Value needed by an active Variant, unless the same transaction completes a valid reconfiguration. | A§6.5 |
| `INV-08` | A composition fingerprint is unique per Product across all Variant history (active, inactive, soft-deleted). A match must be confirmed against the actual pairs. | A§5.3, A§11.1 |
| `INV-09` | A historical inactive Variant cannot be reactivated until its full composition satisfies `INV-02` to `INV-05` against the current configuration. | A§4.5, A§6.3 |
| `INV-10` | A simple Product always retains its original empty-composition Variant identity. Reconfiguration never creates a second empty-composition Variant. | A§4.5, A§6.5 |
| `INV-11` | Product activation requires `INV-06` and a structurally valid configuration. It never depends on price, stock, supplier, or account type. | A§6.2 |
| `INV-12` | The package does not generate the Cartesian product of Option Values. The caller supplies the combinations that are offered. | A§5.4 |

- A Variant belongs to exactly one Product. It carries no price, quantity, or account-type field (DEC-001, DEC-002).

- Composition is immutable after creation. There is no update command for it, and no API accepts a changed composition (A§5.3).
- A change of composition means a new Variant identity and deactivation of the old one. The old identity is never repurposed (A§5.3).
- **SKU/barcode edge cases.** Each is `NULL` or a non-empty string, and an empty string is not stored. A soft-deleted Variant still reserves its values. Replacing or clearing releases the old value. A simple Product's single empty-composition Variant is valid because it has no active Options. The Product's configuration must be valid as a whole: when an active Value of an active Option is represented by no active valid Variant, every Variant of the Product is hidden from the consumer reads, the single get and the list alike, and management reads still show the stored state (A§12, A§6.2).
- Management reads can include inactive and soft-deleted Variants. Consumer reads cannot request deleted records.
- **`VariantDTO` fields.** `id`, `productId`, `sku`, `barcode`, `status`, `displayOrder`, `composition` (the `(optionId, optionValueId)` pairs ordered by numeric `optionId`, empty for a simple Product's Variant), `createdAt`, `updatedAt`, `deletedAt`. The composition is exposed because the Host needs it to map shopper choices to a Variant; the fingerprint is internal and is not exposed (A§5.3). The consumer and management reads return the same DTO.

Rules and edge cases:

- **Fields.** Product Content has `name` (required, at most 255 characters, not empty or whitespace only under any Unicode whitespace), `shortDescription` (optional, at most 500 characters), and `description` (optional, at most 65535 bytes). Option and Option Value Content have `name` only, with the same rules. Values are valid UTF-8 and stored verbatim, never trimmed; an empty optional string is kept and differs from `null`. `name` is a label, not HTML. The package stores and returns values only, and never renders or sanitizes markup (A§4.1, A§11). A violation is `ProductInvalidArgumentException` at Command construction.
- **Identity.** `(owner_id, language_code)` is immutable and unique across soft-deleted history, including the single `NULL` row (A§4.1, A§6.4, A§11.2).
- **Exactness.** An exact-language read for `'ar'` never returns `NULL` content or another language. An exact unlocalized read never returns a localized record. There is no implicit fallback of any kind (A§12, DEC-004).
- **Selectors.** The three selectors are distinct, mutually exclusive typed states. Omitting a language filter and passing `NULL` are different intents and must not share a parameter (A§12).
- **Language edge cases.** `'EN'` and `'en'` are the same identity under the collation. Creating the second is a `FC-CONF`. An empty or whitespace-only non-`NULL` language is a `FC-VAL`.
- **Required labels.** Removing or soft-deleting the last non-empty name of an **active** Product is rejected (`INV-06`, `FC-INV`). The same protection applies to the last label of an active Option, and of an active Value of an active Option (`INV-05`). An inactive owner may lose its last label. Validated on the locked configuration graph.
- **Consumer visibility.** A Content record is visible only if it is not deleted and its owner chain is visible: an active, non-deleted Product, and for Option/Value Content an active, non-deleted Option (and Value).
- **Re-adding.** Creating a Content identity that exists in soft-deleted history is rejected with the owner's `*ContentAlreadyExistsException` and an explicit restore is required (A§17), as for every identity family (see 1.2).
- **Order and bounds.** Management lists order by `language_code` (the unlocalized record first) then `id` and return at most `maxResults` (1 to 100); the paginated read uses `maatify/persistence` with 20 per page by default and at most 100 (see 1.5).

Rules and edge cases:

- **Target and integrity.** A target is the Product or one Variant of that same Product. A Variant of another Product is rejected by the database through the composite key `(variant_id, product_id)`. A Product-level assignment is still anchored to an existing Product through the independent `product_id` key (A§9.3, A§11.1).
- **Identity.** `(target kind, target identity, media_asset_id, role_id, language_code, platform)` is immutable and unique across soft-deleted history. The same Media Asset may be assigned to another target or another exact scope (A§9.3).
- **Default.** At most one active default per exact `(target, role, language, platform)` scope. Default is independent of `display_order`. Soft-deleting or clearing a default never promotes another row. Restore always leaves a row non-default; making a live row default is the explicit set-default operation (`IAS-02`), exactly as in `php-category`, and restoring a soft-deleted row as the default is the separate explicit `IAS-07`, which conflicts instead of replacing a live default (A§9.4, A§11.4).
- **Concurrency.** A default replacement is protected by transaction locking and by a database unique key that treats `NULL` as a real scope value. A plain unique key containing `NULL` is not sufficient (A§9.4, A§11.4).
- **Consumer visibility.** The Product is active and not deleted. For a Variant target, the Variant is active and not deleted. If `role_id` is non-`NULL`, the Role is active and not deleted. The assignment is not deleted. An inactive or deleted ancestor hides the assignment without changing it (A§9.3, A§12).
- **No inheritance.** A Product-level read does not return Variant-level assignments, and a Variant-level read does not return Product-level assignments (A§9.4).
- **Re-adding.** Creating an assignment whose identity exists in soft-deleted history fails with `FC-CONF` identifying the identity; `IAS-05` is the explicit restore, exactly as in `php-category`.
- **No media check.** The package never uploads, resolves, transforms, or verifies the Media Asset (A§9.4, DEC-005).
- **Default operations.** `IAS-02` and `IAS-03` apply to a non-deleted assignment whatever the status of its Role or target (the sources restrict only the creation of a role-scoped assignment to an active Role, A§9.2), and an inactive Role or target only hides the assignment from consumer reads. A soft-deleted assignment cannot be made default by `IAS-02` (the database rejects a soft-deleted default); `IAS-07` restores it in the same update that sets the marker. Set and clear are independent explicit operations, as in `php-category`; creation never selects a default and `display_order` changes never alter it.
- **Default operations under a soft-deleted target.** `setDefault` requires a non-deleted assignment, a non-deleted target Product and Variant, and a non-deleted Role when one is set; `clearDefault` removes the marker of a non-deleted assignment even when its target or Role is soft deleted, promotes nothing, and creates no new default; a soft-deleted assignment can never become default, and no operation promotes a replacement row. A create never sets `is_default`. The management criteria are the exact selectors of `ImageAssignmentListCriteriaDTO` (see *Image Assignment criteria*).

#### 3.8 Cross-family contracts

##### `RES-01` Variant composition resolution (Consumer read, read-only)

`VariantConsumerServiceInterface::resolveByComposition(int $productId, VariantCompositionCriteriaDTO $criteria): VariantDTO`. Resolves a shopper's option choices to one concrete `variant_id`. The Host owns presentation and when to call it. The package owns whether the selection is a real, active, valid Variant (A§5.5).

| Aspect | Contract |
|---|---|
| Input | `product_id` and a typed collection of selection pairs `(option_id, option_value_id)`. No associative array is accepted. An empty collection is valid input. |
| Order | Order-independent. Pairs are canonicalized by numeric `option_id` (A§5.3). |
| Output | The single matching active, non-deleted Variant identity (`VariantDTO`, see 3.9). |
| Rejects (`FC-VAL`, `ProductInvalidArgumentException`) | A repeated Option (by the criteria at construction). An Option or Value from another Product. A Value paired with the wrong Option. An inactive or soft-deleted Option or Value. Incomplete coverage of the active Options. |
| Coverage | For a configurable Product, exactly one active Value for every active Option, with none missing and none extra. |
| Simple Product | An empty selection returns the single active empty-composition Variant, provided the Product and Variant are visible to consumers. A non-empty selection names Options that are not active, so it is rejected (A§5.5 items 3 and 4). |
| Product not visible | A Product that does not exist or is not consumer-visible (inactive or soft deleted) is `FC-NF` (`ProductNotFoundException`), judged before the selection. |
| No match | A structurally valid, complete composition with no matching consumer-visible Variant is `VariantNotFoundException`, including a historical inactive composition and a match hidden by the product-wide visibility rule. |
| Never | It never creates a Variant, never reactivates a historical one, and never invents a default. A matching digest with different pairs is `FC-INT` (`ProductPersistenceException`). |

Examples of composition safety:

- A configurable Product with active Options `{color, size}` and a request carrying only `color` is rejected as partial coverage, even if exactly one Variant has that color.
- A request containing a Value of an inactive Option is rejected, even though a historical inactive Variant still contains it.
- A request equal to a historical inactive Variant's composition returns no active Variant. It does not reactivate it.

##### `CFG-01` Product reconfiguration (Management command, atomic)

`ProductManagementServiceInterface::reconfigure(ReconfigureProductCommand $command): ProductReconfigurationResultDTO`. The only way to change the active Option set or the active Variant set, and the only way to create non-empty Variants. It is a Product-local atomic operation, never a sequence of ordinary Option calls (A§4.5, A§5.4, A§6.5).

Required behavior (A§5.4):

1. Validate the intended new active Option/Value set. Every active Option and every active Value of an active Option needs a non-empty label (`INV-05`).
2. Validate every proposed Variant composition for exact coverage of the active Options. Reject extra inactive or deleted Options, cross-Product values, invalid Values, and duplicate compositions.
3. Create replacement Variant identities with immutable compositions.
4. Deactivate replaced Variants without deleting history. A matching historical composition is a conflict unless the command explicitly names the existing Variant to reactivate or restore.
5. Keep at least one active valid Variant.
6. Establish every Product-local invariant before the operation completes. If a complete valid replacement cannot be produced, the whole operation is rejected (`FC-INV`, `FC-CONF`).

Transitions it must support:

- **Simple to configurable.** Establish the new active Option set, create complete replacement Variants, and deactivate the empty-composition Variant in the same transaction.
- **Configurable to simple.** Deactivate every active Option and every active non-empty Variant. Reactivate or explicitly restore the original empty-composition Variant. Retain Options and Values as history. Never create a second empty-composition Variant. If the original is missing or invalid, fail closed and report why (`FC-INT`).
- **Configurable to configurable.** Replace the set, reactivating historical Variants only by explicit identity.

Boundaries:

- It never calls Pricing, Inventory, or Supplier, and never copies or transfers their records. New Variants inherit nothing (A§5.4, A§14). The Host/Catalog coordinator reconciles external mappings before it reactivates a historical Variant (A§4.5).
- Its result lets the Host see the deterministic old and new Variant identities (A§14): `ProductReconfigurationResultDTO` lists the Variant identities created (in request order), reactivated, restored, and deactivated, and the Option and Option Value identities activated and deactivated.

**Reconfiguration contract:**

- **Input.** `ReconfigureProductCommand(productId, options, variants)`: `options` is a list of `ReconfigureOptionTarget(optionId, activeOptionValueIds)`, the complete target set of active Options each with the complete set of its active Values; `variants` is a list of `ReconfigureVariantTarget(composition, reuseVariantId)`, the complete target set of active Variant compositions as `OptionValueSelection` pairs with an optional reuse identity. The command is a complete target state, not a list of deltas. It carries no `sku` or `barcode`: new Variants start with `NULL`, and `VAR-01` owns those identifiers.
- **Prepared members only.** Options and Values must already exist under the Product, be non-deleted, and have a label; the operation activates and deactivates them and never creates them. Options outside the target set are deactivated and their Values are kept unchanged as history; Values of a target Option that are not listed are deactivated.
- **Variants.** An active Variant absent from the target becomes `inactive` and keeps its history. A composition that already exists in the Product's history (active, inactive, or soft deleted) is reused only when `reuseVariantId` names that Variant, after confirming the actual pairs and the owning Product; an inactive one is reactivated and a soft-deleted one is restored, revalidated, and activated inside the same operation. A new composition becomes a new active Variant. The transition to a simple Product names the original empty-composition Variant; a second empty-composition identity is never created, and a configurable target allows no empty composition.
- **Rejections.** Duplicate compositions, incomplete or extra coverage of the target Options, Values of another Product or outside the target set, an unrepresented target Value, and a target with no active valid Variant are rejected, and every failure rejects the whole operation with no partial write.
- **Failure classes.** A malformed typed input or a repetition inside the request: `FC-VAL`. An existing composition without a reuse identity, or an identity conflict: `FC-CONF` (`VariantCompositionConflictException`). A target that violates an invariant: `FC-INV`. A fingerprint that does not match the stored pairs, or a missing original empty-composition Variant for the transition to simple: `FC-INT`. A missing Product: `FC-NF`; an unknown reuse identity: `VariantNotFoundException`.
- **Transaction and locks.** `PdoSavepointTransactionRunner`; the Product row is locked first, then Options, Option Values, and Variants in ascending `id`, before any state the operation builds on is read; every Product-local invariant is validated before commit.

**Reconfiguration model and its basis in the architecture:**

| Question | Answer | Basis |
|---|---|---|
| Target state or deltas | **Declarative target state.** The input is the intended active Option and Value set plus the proposed Variant compositions; validation is against that whole set. | A§5.4 items 1 to 3 validate "the intended new active set" and "every proposed composition" |
| An active Variant omitted from the proposed set | It is **deactivated, never deleted**; its identity and history stay. | A§5.4 item 4 ("deactivates replaced Variants without deleting historical identities") |
| Creating Options and Values inside the operation | **Not allowed.** They are created inactive through their own commands so codes and labels can be prepared; the operation only activates or deactivates prepared ones. | A§5.4 first bullet, A§6.1 |
| Soft delete and restore inside the operation | **No soft delete.** Options and Values are retained as history and deactivated. The only restore is the explicit restore of the Product's original empty-composition Variant (and of a named historical Variant). | A§4.5, A§6.5 |
| State of replacement Variants | Non-empty Variants are created **active** as members of the validated set; a historical Variant becomes active again only when named explicitly and revalidated. | A§4.5, A§5.3, A§6.3 |
| Transaction and locking | One local transaction through the savepoint runner; the Product row is locked first, before any read of the current configuration; all invariants (`INV-01` to `INV-10`) are validated before commit and any failure rejects the whole operation. | A§6.5, A§11.6, A§14 |
| Type shapes and lock order | As in the reconfiguration contract above. | A§11.6 |

### 5. Consumer Workflow

This is the contract path required by Package Building §25. Runnable code is in [`examples/`](examples/) and the [Usage Guide](docs/guides/USAGE_GUIDE.md).

```text
Host input
   -> typed Command / Criteria
   -> Management or Consumer service (Product aggregate lock for mutations)
   -> shared persistence boundary (MySQL 8.0.16+, direct PDO, Ordering, Pagination, Transaction)
   -> typed result, or a documented package exception
```

Typical flows:

1. **Catalog setup.** Create a Product (`PRD-01`). Add Content with a name (`CNT-01`). Activate it (`PRD-02`).
2. **Make it configurable.** Create Options (`OPT-01`) and Values (`OVL-01`) while inactive. Add labels (`CNT-01`). Run reconfiguration (`CFG-01`) with the offered combinations.
3. **Shopper selection.** The Host reads the visible Variants (`VAR-R2`), collects the shopper's choices, and calls resolution (`RES-01`). It gets one `variant_id`, and passes that to Pricing, Inventory, or an order.
4. **Presentation.** The Host reads the selectable Options (`OPT-R2`) and Values (`OVL-R2`), exact Content (`CNT-R2`), and exact-scope image assignments (`IAS-R2`), applying its own fallback. Runnable in [`examples/05-consumer-presentation.php`](examples/05-consumer-presentation.php).

### 6. Open Contract Gaps

No open contract gaps. A gap found later is added here with its sources, its impact, and the kind of resolution it needs; authority follows `std-ai-collaboration-workflow` §3.2.1, and the affected contract is not implemented on an assumption.

## Operational Read / Reporting Classification

This section records the classification required by Package Building Standard §15.

**Classification: In Scope.**

**Reason.** §15 decides applicability by what the package owns, not by whether it uses a database. `php-product` owns persisted domain state with its own lifecycle and invariants (architecture §3.1, §4–§6, §9):

- Product identity and its `active`/`inactive` status and soft-deletion state;
- Variant identity and lifecycle, including the immutable composition;
- Option and Option Value identity and lifecycle;
- optionally localized Product, Option, and Option Value Content;
- Product Image Roles and Product/Variant Image Assignments, including default and ordering state.

These are package-owned statuses and assignments of the kind §15 names, so the capability cannot be classified Not Applicable. The persistence engine is not the justification.

### Read Contracts

The Host must be able to understand and manage this state without querying Product tables or reimplementing Product invariants. The approved architecture (§12, §13) establishes two distinct use cases, so the contracts stay separate. They are PHP-level, framework-agnostic, typed, and read-only. The capability IDs in the [Approved Contract Inventory](#approved-contract-inventory) are the inventory of these contracts. Exact names and signatures are in the [Implemented Public API](#implemented-public-api).

| Use case | What it covers | Visibility boundary |
|---|---|---|
| **Management reads** | Listing of Products, Variants, Options, Option Values, Content, Image Roles, and Image Assignments with explicit status (where the family has one) and deleted-state filters; a literal code search for Products only; and business-key reads by Product code and Image Role key. | Can include `inactive` and soft-deleted records, because the Host needs to administer them. Unpaginated lists return at most 100 records. Large lists use the shared `maatify/persistence` pagination (`PageRequest`/`PageResult`), not a package-local engine. |
| **Consumer reads** | Variant listing for a Product, Variant composition resolution (§5.5), selectable Options and Option Values, exact Content reads, and exact-scope image-assignment reads. | Return only records valid under the visibility invariants: an active, non-deleted Product with structurally valid, active, non-deleted Variants and Options. A Variant appears only if every Option Value in its composition is active and not soft-deleted, belongs to the selected Option and to that Product, and the composition covers exactly the Product's active Options, one value per active Option with none missing, extra, or invalid (§5.5, §6.2, §6.3), and only while every active Value of an active Option of the Product is represented by such a Variant. A simple Product's single empty-composition Variant is valid because it has no active Options. An inactive or deleted ancestor suppresses its children without changing them. Consumer reads cannot request deleted records or bypass these rules. |

Both use cases keep the architecture's read semantics:

- Content reads are exact. The typed criteria distinguish an exact language, unlocalized-only (`language_code IS NULL`), and all languages (management only). There is no implicit fallback to `NULL` or another language.
- Image assignment reads use the exact target, role, language, and platform scope, where `NULL` means exactly `NULL`.
- Lists are ordered deterministically (`display_order, id`) where ordering applies. `Product` itself has no `display_order` (`DEC-006`).
- Composition resolution is read-only. It never creates or reactivates a Variant and never invents a default.

### Domain Boundaries and Non-Goals

- Reads cover only data and meanings Product owns. They never join Host, Category, Pricing, Inventory, Supplier, Order, Customer, or Media storage tables, and they never use another package's internal storage.
- Product queries do not claim a Product is "in stock" or "sellable", because Product reads neither Inventory nor Pricing (architecture §12, §15). Sellability is derived by the Catalog/Host layer.
- Cross-package and Host-specific aggregation belongs to the Host or Project-Aware scope.
- Product adds no HTTP routes, controllers, middleware, permissions, UI dashboards, exports, or Host actor/name resolution.
- No generic `Dashboard`, `ReportService`, or metrics abstraction is part of the package. None is added for compliance.

### Intentionally Unsupported Reporting Dimensions in V1

The approved architecture establishes no meaning for any of the following, so Product V1 does not provide them. Adding one needs an Owner-approved change to the architecture contract.

- counts, aggregates, grouped results, or status summaries beyond the pagination metadata supplied by `maatify/persistence`;
- time-window summaries and audit or history reads, beyond the application-managed `created_at`, `updated_at`, and `deleted_at` fields on the records themselves;
- price, availability, stock, supplier, order, or sellability reporting, which belongs to other domains;
- Category-based grouping or ordering, because Product-to-Category mapping is outside the package (`DEC-006`).

### Verification Obligation

Any read result that depends on persisted state, including exact language and scope matching, visibility suppression, deleted-state filtering, ordering, and pagination, requires Integration evidence on the supported persistence engine (MySQL `8.0.16+`). Unit mocks alone are not sufficient (§15; architecture §17).
